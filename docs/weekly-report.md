研究任务：智能眼镜 Agent 的CUA评测（Glass Use）
</callout>

<callout emoji="🔸">
**为什么研究 Glass-Use**
智能眼镜正在从主要用于拍摄、识别和问答的穿戴设备，逐渐发展为能够持续接收第一人称视觉和语音、并向用户反馈任务状态的新型计算入口。它与电脑和手机最重要的区别，不只是设备形态更小，而是能够直接看到用户正在看的现实环境。用户不必先把眼前的对象和场景完整描述成文字，而可以自然地说“帮我买这个”“把这张发票报销掉”或“给这台设备报修”。这使智能眼镜特别适合用户双手被占用、正在移动，或不方便操作屏幕的场景。
**市场为什么在此时值得关注**
智能眼镜已经从少量概念产品进入多家厂商同时投入、产品开始规模出货的阶段。根据 [IDC](https://www.idc.com/resource-center/blog/2025年中国智能眼镜市场同比增长87-1，行业从硬件铺陈/) 的统计，2025年全球智能眼镜出货量为1477.3万台，同比增长44.2%；中国市场出货量为246.0万台，同比增长87.1%。这一规模仍远小于手机，不能说明智能眼镜已经成为成熟的大众终端，但它表明行业正在从原型验证走向真实用户和渠道验证。更重要的是，参与者已经不只有传统眼镜或AR创业公司，还包括拥有大模型、操作系统、手机、社交网络和生活服务生态的平台厂商。
目前有代表性的产品大致形成了三条路线：
1. **先做成能够日常佩戴的“相机、耳机和AI助手”**。[Ray-Ban Meta](https://about.fb.com/news/2025/05/ray-ban-meta-glasses-come-to-india-experience-the-future-with-meta-ai-integrated-and-multiple-styles-on-offer/) 以普通眼镜外形提供第一视角拍摄、语音问答、翻译、通话和社交分享；[华为 AI 眼镜](https://consumer.huawei.com/cn/audio/ai-glasses/) 与 [小米 AI 眼镜](https://www.mi.com/global/discover/article?id=5172) 也采用相近的无显示路线，同时把眼镜接入各自的手机、语音助手和设备生态。这类产品不需要在镜片上显示图像，更容易把重量和续航控制在适合日常佩戴的范围，因此最先形成了出货规模。
2. **在轻量眼镜中加入显示，让系统能够在用户视野内反馈结果。**[Meta Ray-Ban Display](https://about.fb.com/news/2025/09/meta-ray-ban-display-ai-glasses-emg-wristband/) 已加入彩色显示和腕带交互；[Rokid Glasses](https://global.rokid.com/blogs/news/rokid-launches-worlds-lightest-full-function-ai-ar-smart-glasses) 与 [RayNeo X3 Pro](https://www.rayneo.com/pages/x3-pro-launch) 把第一视角相机、语音，以及能够将导航和翻译等简短信息投到视野中的显示装置放入较轻的镜框；阿里的[夸克 AI 眼镜 S1/G1](https://www1.xinhuanet.com/tech/20251127/08d77754e3654647b345f1b71ca496c1/c.html)则把千问与搜索、导航等服务结合。显示让眼镜不再只能“听到回答”，而可以承担任务状态、关键选择和风险确认等简单界面。
3. **把眼镜发展成新的操作系统和应用平台。** Google 正与 Samsung、Gentle Monster 和 Warby Parker 建设 [Android XR 智能眼镜生态](https://blog.google/products-and-platforms/platforms/android/android-xr-io-2026/)，并明确区分语音反馈型眼镜和带显示眼镜；XREAL、Rokid、RayNeo 等厂商也在提供系统和开发工具。竞争因此开始从单件硬件转向“谁能连接更多应用和服务、形成可持续的开发者生态”。
智能眼镜有潜力成为下一代个人计算终端，并不只是因为它把屏幕戴在了脸上，而是因为它同时具备三个手机难以持续提供的条件：始终与用户视角一致的第一人称感知、可以随时发起任务的免手持语音交互，以及贴近视线或耳边的即时反馈。如果这些能力再与网页、手机应用和企业系统中的执行能力连接起来，眼镜就可能从手机的拍摄和通知配件，进一步变成用户访问数字服务的入口。它未必会在短期内替代手机，但有可能像智能手表一样先成为长期佩戴的伴随终端，并逐步承接部分原本必须拿出手机完成的任务。
市场增长也不等于关键问题已经解决。IDC 同时指出，当前多数产品的AI功能仍集中在拍摄、问答、翻译、识物和导航，真正能让用户长期使用的场景以及跨应用执行能力尚未形成；续航、隐私、交互方式和显示能力也仍在快速变化。换句话说，硬件已经开始进入市场，但“眼镜上的智能体应该如何理解现实需求、可靠调用数字服务，并让用户看得懂和管得住”还没有形成共同答案。
这构成了本项目的研究窗口。如果等到操作系统、应用接口和产品形态完全定型后再研究，能做的往往只是适配既有平台；而在生态尚未固化时建立 Glass-Use 的任务定义、可归因评测和安全边界，可以更早回答什么能力才构成可靠的眼镜智能体，并形成可被后续设备和平台复用的评价基础。这里所说的“提前占据生态位”，不是预设智能眼镜一定取代手机，而是在下一代智能终端仍在形成时，先占据“现实感知如何可靠连接数字执行”这一明确、可长期积累的研究位置。
但只回答“眼前是什么”还没有充分发挥这种入口的价值。现有智能眼镜研究主要集中在视觉问答、场景理解、检索和长期记忆，任务通常在模型给出答案时结束。与此同时，Tool-Use Agent 和 Computer-Use Agent 已经能够调用工具，或在网页、手机和电脑界面中完成搜索、填写、提交等操作。将两者结合后，智能眼镜就不只是一个感知设备，而可以把现实世界中自然产生的需求交给数字系统执行，形成以下闭环：
> 第一人称现实感知 → 理解用户意图 → 确定用户所指对象 → 对齐数字系统中的具体实体 → 调用工具或操作界面 → 向眼镜反馈进度并请求必要确认 → 检查最终结果
本项目把能够完成这一闭环的系统称为 **Glass-Use Agent**。例如，用户看着一件商品说“帮我买这个”时，Agent 不仅要识别商品，还要在电商网站中找到对应的具体款式并完成操作；用户看着一张发票说“帮我报销”时，Agent 还要把票面信息对应到正确项目，在报销系统中填写表单，并在提交前让用户确认关键信息。这里真正需要研究的不是单独的视频理解，也不是单独的网页操作，而是两者之间能否可靠衔接。
这种衔接带来了电脑和手机 Agent 中不突出的新问题：
1. 用户的指令依赖持续变化的现实环境，常出现“这个”“刚才那个”等指代，眼前对象也可能在任务执行过程中发生变化；
2. Agent 必须把现实中的商品、设备、票据或人员准确对应到网页或业务系统中的商品编号、资产记录、费用或联系人，实体对应错误会直接导致操作对象错误；
3. 用户可能在执行过程中补充要求、改变目标，或者因为原指令不够清楚而需要 Agent 主动追问；
4. 具体操作往往发生在云端浏览器、手机、电脑或企业系统中，而眼镜显示空间有限，用户难以像盯着电脑屏幕一样持续检查执行过程，因此还涉及状态反馈、风险确认和结果验证。
现有研究已经分别积累了第一人称视频理解、可穿戴视觉问答、可穿戴语音、工具调用和电脑操作等数据与评测，也出现了将眼镜连接到通用 Agent 的系统原型；但这些能力大多仍被分开评估。第一人称数据集通常只检查模型是否理解视频，Computer-Use Benchmark 通常只检查模型能否操作数字界面，现有系统原型则较少提供可复用、可归因的统一评测。因此，目前仍难回答一个更接近真实使用的问题：当任务从现实环境出发、最终在数字系统中产生结果时，Agent 是否始终理解了正确对象，能否应对中途变化，并完成可验证的正确操作。
因此，研究 Glass-Use 并不是简单地把现有 Computer-Use Agent 搬到眼镜上，而是研究一种新的现实—数字协同方式：由眼镜提供连续的现实上下文，由 Agent 负责跨系统执行，同时让用户能够在必要时补充、纠正和确认。建立相应 Benchmark，可以把这条完整链路拆开验证，判断当前模型距离可实际使用还差在哪些能力，也为后续的安全性和眼镜端交互研究提供共同基础。

想法1：
现有工作已经开始将智能眼镜的第一人称感知接入真实数字系统执行，例如 Ego2Web 接 Web Agent、VisionClaw 接 OpenClaw、Egocentric Co-Pilot 接 Web 工具箱。但现有评测大多只报告端到端成功率，无法明确判断任务失败发生在哪个环节。
考虑将完整链路拆分为2个阶段，并分别提供 Ground Truth：
1. 用户意图理解：通过模糊的指令和第一人称视频抽帧判断用户意图 （最难的一步）
2. 导航与执行：是否在正确实体上完成用户要求的操作。
核心假设是：当前 Glass-Use Agent 的主要瓶颈可能在用户意图理解上（智能眼镜本身第一人称带来的视觉干扰和语音带来的噪声干扰），而现有工作更多关注第2阶段的 Web 或 GUI 执行。该 Benchmark 可以将黑盒式端到端成功率转化为可归因的诊断结果。
想法2：
Glass-Use Agent 会基于现实环境信息操作数字系统，因此除了任务成功率，还需要评估执行阶段的安全性。
考虑三类风险：
1. 实体链接错误：Agent 是否会因为视觉指代或实体链接错误，对错误的商品、设备、联系人或账户执行操作；
2. 用户授权：Agent 是否会在缺少明确用户授权的情况下发送消息、提交表单、下单或上传信息；
3. 隐私：Agent 是否会将旁观者的人脸、屏幕、文件或对话等隐私内容纳入上下文并上传到云端。
还可以进一步加入物理环境提示注入和数字界面提示注入，评估恶意文字是否会最终触发真实的数字副作用。目前 Glass 领域缺少针对上述风险的系统性安全 Benchmark。
想法3（思考中）：
与传统 Computer-Use Agent 或 Phone-Use Agent 不同，智能眼镜中的 Agent 执行过程具有更强的“不可见性”。
在电脑或手机场景中，用户可以直接观察 Agent 的操作过程，例如鼠标点击、页面跳转、输入内容以及当前界面状态。当 Agent 执行错误时，用户通常能够及时发现并进行干预。
但在 Glass Agent 场景中，用户主要通过光波导显示、语音反馈或简单状态提示了解 Agent 的执行过程。由于眼镜显示空间有限，复杂任务的中间状态很难完整呈现。例如：
- Agent 当前理解的目标对象是什么；
- Agent 正在访问哪个数字系统；
- Agent 如何从现实物体映射到数字实体；
- Agent 当前执行到了哪一步；
- Agent 是否已经选择了正确的信息来源。
这些关键状态对于用户来说往往是不可见的，因此用户难以判断 Agent 是否正在沿着正确路径执行。
进一步而言，这会导致两个问题：
1. **过程不可验证**
用户无法像在电脑屏幕前一样观察 Agent 的每一步操作，因此难以及时发现错误。例如用户说“帮我买刚才看到的白色外套”，Agent 可能已经错误地识别了另一件衣服，但由于执行过程不可见，用户直到最终结果生成后才发现问题。
1. **结果不可验证**
由于用户无法观察 Agent 的推理链路和关键决策依据，即使最终结果呈现出来，用户也很难判断结果是否可靠。例如：
- 找到的商品是否就是用户看到的那件；
- 提交的表单是否填写了正确的信息；
- 创建的预约是否对应正确地点；
- 上传的文件是否包含不应该上传的信息。
因此，Glass Agent 中的 A2UI（Agent-to-UI）不仅承担传统 UI 的信息展示作用，还承担“建立用户信任”的作用。
一个关键研究问题是：
> 在有限的眼镜显示空间和低打扰交互约束下，A2UI 应该展示哪些 Agent 状态，才能帮助用户理解、监督和控制 Agent 行为？
可能需要研究：
- **任务意图展示**：Agent 当前理解用户想完成什么；
- **目标对象展示**：Agent 当前认为用户指向哪个现实对象；
- **关键决策展示**：Agent 使用了哪些关键信息完成判断；
- **执行状态压缩**：如何将长流程任务压缩成用户可理解的状态摘要；
- **风险节点提示**：在哪些步骤必须要求用户确认；
- **可恢复交互**：用户发现错误后如何快速修改、撤销或重新规划任务。
核心假设：
> Glass Agent 的关键挑战不仅是“能否完成任务”，而是“能否让用户理解 Agent 正在完成什么任务，以及是否值得信任”。
相比 Computer-Use Agent，Glass Agent 可能需要一种新的 Agent 可解释交互范式：不是展示所有执行细节，而是在有限空间中展示影响用户判断和授权决策的关键信息。

论文故事线：
1. 背景
现有智能眼镜正逐渐从概念产品发展为面向真实生活场景的新型终端设备，例如 Rokid Glasses、Qwen Glasses 等。与传统计算终端不同，智能眼镜能够通过摄像头获取第一人称视觉信息，同时通过麦克风接收用户的语音指令，为 Agent 提供来自真实环境的多模态上下文。
在这一交互模式下，用户可以通过自然语言提出需求，模型结合眼镜当前采集到的视觉信息理解用户所指向的物体、场景或事件，从而完成视觉问答、物体识别、信息检索和环境理解等任务。目前，这类应用主要集中在 VQA、视觉理解和 RAG 等方向。
然而，现有研究较少进一步探索如何将 Tool-Use Agent、CLI Agent 或 Computer-Use Agent 与智能眼镜结合。智能眼镜不仅可以成为 Agent 感知真实世界的入口，还可以作为用户发起任务、查看执行状态、进行干预和确认的交互终端。Agent 则可以在云端、计算机、手机或企业系统中完成具体操作，形成“现实环境感知—任务理解—数字系统执行—结果反馈”的完整闭环。
这一方向可以进一步抽象为 **Glass-Use Agent**：Agent 通过智能眼镜理解用户所处的真实环境，根据用户指令调用工具或操作数字系统，并通过眼镜向用户反馈执行进度和最终结果。
1. 问题
（1）现有工作主要关注端到端任务是否完成，即报告最终成功率。然而，在 Glass-Use 场景中，一个任务失败可能来自多个不同阶段。例如，用户说“帮我找到刚才看到的白色外套”，Agent 失败可能是因为没有理解用户指向的视频片段，也可能是因为没有找到对应商品实体，或者已经找到正确商品但网页操作失败。单一的端到端成功率无法揭示 Agent 的真实能力瓶颈。因此，一个重要问题是：**Glass-Use Agent 的失败究竟发生在哪里？是现实理解失败、实体链接失败，还是os执行失败？**
（2）此外，由于 Glass Agent 长时间接触真实环境，其安全问题也更加复杂。Agent 不仅可能受到数字世界中的网页、邮件和文档提示注入影响，还可能受到现实环境中的物理提示注入影响。例如，环境中的文字、屏幕内容或标签可能被错误地理解为用户指令。同时，摄像头持续采集现实世界，也带来了旁观者隐私泄露、敏感信息上传和错误实体操作等风险。因此，需要进一步研究：**Glass-Use Agent 在真实环境中是否能够安全地执行任务，并保持用户对 Agent 行为的控制权。**
（3）Glass-Use Agent 还面临新的用户交互和信任问题。与电脑和手机不同，智能眼镜中的执行过程很难完整展示给用户。用户无法像观察屏幕操作一样看到 Agent 的搜索过程、页面变化和中间决策，只能通过有限的光波导显示、语音反馈或状态提示了解任务进展。这导致用户难以判断 Agent 是否理解正确、是否操作了正确对象以及最终结果是否可信。因此，另一个关键问题是：**在有限显示空间下，Glass Agent 应该如何设计 A2UI（Agent-to-UI），让用户能够理解、监督并控制 Agent 的行为？**

## 主要结论（成功和失败的结论都需要写，都是重要经验）

<callout emoji="🎨">
本周主要完成 Glass-Use 方向的选题梳理、相关工作核查和数据可行性分析，暂未开展正式实验。当前形成三条候选研究路线：第一是对 Glass-Use Agent 的失败进行分阶段归因；第二是评估其在错误实体操作、用户授权和隐私方面的安全风险；第三是研究有限眼镜界面下的执行可验证性与 A2UI 设计。三条路线并非完全独立，分别对应“哪里容易出错”“错误会产生什么后果”以及“用户能否发现错误”。
**C1：当前优先考虑可归因诊断方向。** 现有工作已经将第一人称视频连接到 Web Agent 或通用工具系统，但多数仍以端到端成功率作为主要指标。该指标无法区分失败发生在视觉指代、现实—数字实体链接还是 Web 执行阶段。相比单纯增加更多任务，将完整链路拆分为可独立验证的中间阶段，可能更有助于定位 Glass-Use Agent 的实际瓶颈。
**C2：Ego2Web 是想法 1 最直接的相关工作，但是这个项目的代码完整性存在问题（缺少统一的agent harness）。** Ego2Web 的公开数据主要包含视频编号、文本指令、任务领域和视觉时间区间，没有提供 bbox、商品 URL、SKU 或其他实体级 Ground Truth。其判定主要依赖 LLM Judge 从指令中抽取关键点并结合执行截图判断结果，因此更适合评估整体任务完成情况，但较难严格验证 Agent 是否操作了正确的实例级实体。
**C3：Glass-Use 的安全评测仍有较明确的研究空间。** 桌面、手机和工具调用场景已经存在 RiOSWorld、OS-Harm、OSGuard、MobileSafetyBench 和 AgentDojo 等安全评测，但目前调研到的工作较少专门覆盖智能眼镜入口。已有 Benchmark 主要建模用户指令和攻击内容之间的冲突，而旁观者的人脸、屏幕、文件和对话被意外采集或上传的问题仍缺少系统评估。但是目前数据采集比较难，较难实现。
